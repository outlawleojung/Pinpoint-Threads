# Pipeline B: 스하리 (팔로워 부스팅)

## 1. 목적

계정 팔로워 자연 증가. 상호 노출·상호 팔로우로 초기 지수 부스팅.

## 2. 명명 vs 실체

**"스하리" 이름은 스레드 팔로우 + 하트 + 리포스트 3종 세트에서 왔으나, 이 프로젝트는 실제로 "팔로우백"만 수행.** 하트·리포스트·감사 댓글은 하지 않음. 이유:
- API rate limit 절감
- Meta CIB 감지 회피 (액션 다수 = 봇 패턴)
- 팔로우백만으로도 팔로워 증가 목적 달성

## 3. 발행 규모 & 스케줄

| 항목 | 값 |
|---|---|
| 하루 발행 | 계정당 1건 |
| 발행 시간 | 아침 08:00~08:30 |
| 4계정 합산/일 | 4건 |

## 4. 소스 선정 (병행 전략)

두 방식을 동시 운영:

### 4.1. 사전 축적된 "스하리 글 모음"
- 사용자님이 그동안 수동으로 사용해온 검증된 문구 풀
- DB에 저장, 계정별·요일별 다변화 (같은 것 반복 노출 방지)
- 새 소스가 반응 좋으면 이 모음에 자동 추가

### 4.2. 해시태그 검색 (실시간 트렌드)
- `#스하리1000명프로젝트` 등 검색어로 크롤링
- 반응 좋은 것 상위 K개 → Copywriter가 페르소나 각색
- 크롤링 방식은 [05-data-collection/strategy](../05-data-collection/strategy.md) 참조

## 5. 발행 흐름

```
[08:00~08:30 계정별 시차 발행]

1. Suhari Source 선정
   ├─ 모음에서 선택 (accountId + dayOfWeek 해시)
   └─ or 해시태그 상위 반응 큐레이션

2. Copywriter (Sonnet)
   → 페르소나 톤으로 각색

3. Approval Gate (Telegram)

4. Publisher — 발행 (하루 1건)
```

## 6. 발행 후 감시 & 팔로우백

```
[하루 종일 폴링]

5. Comment Watcher (30분 간격 폴링)
   → 오늘 스하리 게시글에 새 댓글 있는지 확인

   (댓글 발견)
      ↓
6. Follow Verifier
   → 그 댓글 작성자가 실제로 내 계정 팔로우했는지 검증
   → 팔로우 안 했으면 무시

   (팔로우 검증 통과)
      ↓
7. Engagement Worker — Reciprocation
   → 팔로우백 실행 (하트·리포스트·답글 없음)
   → 실행 전 10~30분 랜덤 지터
   → 그날 카운터 +1
      ↓
   [카운터 검사]
   → 오늘 3~5회 (매일 랜덤 결정) 도달 시 워커 즉시 셧다운
   → 나머지 댓글은 무시
```

## 7. 하드 룰

- **팔로우백 하루 3~5회 상한** — 매일 아침 그날 상한 랜덤 결정 (봇 감지 분산)
- **초과 시 즉시 셧다운** — 그날 남은 댓글 무시, 다음날 리셋
- **랜덤 지터 10~30분** — 댓글 감지 후 팔로우백까지의 딜레이
- **팔로우 검증 필수** — 상대가 안 따랐으면 팔로우백 안 함 (일방 팔로우 방지)
- **자체 4개 계정끼리 절대 금지** — 스하리 대상은 반드시 외부 사용자
- **하트·리포스트·답글 안 함** — 팔로우백만

## 8. 계정 페르소나 & 다변화

- 4개 계정 모두 스하리 참여
- 계정별 페르소나 seed로 스하리 문장 다변화 → 같은 소스라도 다른 문장
- 소스 선정 시 `(accountId + dayOfWeek)` 해시로 안정적 다양성

## 9. 미결 (Open Questions)

### 9.1. "스하리 글 모음" 데이터 이관
사용자님이 그동안 수동으로 관리한 스하리 문구 풀을 어떻게 시스템에 이관할지.
- 지금 몇 개 정도 갖고 계신지?
- 파일 형태(엑셀·메모)로 있으신지, 헤드에만 있으신지?
- 이관 방식 정의 필요

### 9.2. 해시태그 크롤링 방식
- Threads 공식 API의 `keyword_search`는 별도 승인 필요 (`threads_keyword_search`)
- Playwright vs Apify vs 수동
- [05-data-collection/strategy](../05-data-collection/strategy.md)와 통합 결정

### 9.3. 팔로우백 실행 방법 — ✅ 결정: **거의 완전 수동 + AI 후보 추천**

**Threads Graph API 정밀 조사 결과** (2026-08-31, threads-api-expert):

| 기능 | 공식 API | 결과 |
|---|---|---|
| 자동 팔로우/언팔로우 실행 | ❌ 없음 (`threads_manage_follows` 스코프도 없음) | 수동 |
| 팔로워 목록 조회 (`/me/followers`) | ❌ 없음 | 자체 DB 추적만 가능 |
| 팔로잉 목록 조회 (`/me/following`) | ❌ 없음 | 자체 DB 추적만 가능 |
| 특정 사용자 나를 팔로우 여부 검증 | ❌ 없음 | **불가** |
| 댓글 작성자 정보 | 🟡 `username`만 (numeric id · bio · 팔로워 수 미제공) | 부분 사용 가능 |
| Insights aggregate | ✅ `followers_count`, `follower_demographics` 등 총합만 | 개별 관계 판정 불가 |

**결정: 시스템은 후보 추천만, 팔로우 액션·검증은 사용자가 수동**

- **자동 (시스템)**:
  - Comment Watcher가 30분 간격으로 내 스하리 게시글의 새 댓글 감지
  - 댓글 작성자 username 목록 수집 (제공 정보 한정)
  - Telegram 알림: "이 사용자들이 오늘 스하리 댓글 남김. 앱에서 프로필 확인 후 팔로우 여부 판단하시고 팔로우백 하세요"
  - 로컬 DB에 팔로우백 실행 기록 (사용자가 앱에서 팔로우한 뒤 텔레그램 콜백으로 "완료" 표시)
  - 하루 3~5회 카운터 관리 (사용자가 초과하지 않도록 카운트다운 표시)

- **수동 (사용자)**:
  - 텔레그램 알림 받고 Threads 앱 열기
  - 각 댓글 작성자 프로필 → 나를 팔로우했는지 눈으로 확인
  - 팔로우했으면 팔로우백 (앱에서 1탭)
  - 텔레그램에서 "완료" 버튼 클릭 → 카운터 +1

**하루 총 소요 시간**: 3~5건 × 30초 = 1~3분

### 왜 이렇게 결정했는가

1. **자동 팔로우 자체가 공식 API로 불가능** — 우회하려면 비공식 API or Playwright 자동화 → 계정 정지 리스크
2. **팔로우 검증도 API로 불가능** — "이 사람이 나를 팔로우했나?"를 확인할 방법 없음. 사람 눈으로만 판단.
3. **계정 정지 손실 >> 수동 절감 이득** — 하루 1~3분 절감하려고 계정 밴 감수할 수 없음
4. **원칙 명문화**: CLAUDE.md 최소 규칙에 "계정 정지 리스크 있는 자동화 절대 금지" 포함

### 시스템이 할 수 있는 최대치

- 스하리 게시글 발행 자동화 ✅
- 댓글 폴링 · 후보 목록 수집 ✅
- Telegram 알림 · 대시보드 ✅
- 하루 카운터 관리 ✅
- 성과 회수 (스하리 게시글의 댓글·좋아요 수) ✅

**팔로우 액션 자체만 사용자 몫.** 이걸 자동화하지 않는 것이 이 프로젝트의 안전선.

### 향후 변화 대응

Meta가 Threads Graph API에 팔로우 관련 엔드포인트 추가하면 재검토. 지금은 미지원 확정.

## 10. 결정 사항 (Decisions)

- 팔로우백만 수행 (하트·리포스트·답글 없음) (§ 2)
- 소스 병행 전략: 모음 + 해시태그 (§ 4)
- 하루 3~5회 상한 매일 랜덤 결정 (§ 7)
- 자체 계정끼리 절대 금지 (§ 7)
- **팔로우백은 반자동** — 감지는 시스템, 실행은 사용자 (§ 9.3)
- **계정 정지 리스크가 있는 자동화는 절대 금지** (§ 9.3)
