# 성과 피드백 루프 설계 (Performance Feedback Loop)

- 날짜: 2026-09-06
- 상태: 설계 확정 (실측 검증 완료), 구현 대기
- 목적: vision.md의 "터진 게시글의 왜 터졌는가를 재생산" 을 실제로 동작시킴. 성과 데이터를 (a)카피 학습 + (b)확산 결정에 되먹임.

## 1. 배경 · 문제

발행 → 성과 측정(PostInsightSnapshot 24h·72h)까지는 있으나 **"성과 → 학습"이 끊겨** 있음. 카피는 여전히 외부 벤치마크만 참고하고, 우리가 실제로 잘 터뜨린 글에서 배우지 않음. 5계정 동일 콘텐츠 동시 발행 문제도 "성과 게이팅 확산"으로 풀어야 함.

## 2. 실측 근거 (2026-09-06 · 뇌피셜 배제, 데이터로 도출)

25 PUBLISHED 게시글 스냅샷 분석 결과:

**스냅샷 커버리지 (입력 건강도)**: 나이 24h+ 게시글 대부분 24h·72h 정상 수집. 진짜 누락 1건(sookck 쇼핑 92h)뿐. delayed 잡 정상 대기. → **입력 신뢰 가능.**

**쇼핑 (11건)** raw 조회/좋아요: `55/3 127/2 5/4 11/3 14/2 29/3 41/2 67/1 3024/81 32/5 221/4`
- 명백한 히트 1개(3024/81) + 나머지 5~127조회·좋아요1~5로 뭉쳐 **미세 순위 = 노이즈** (좋아요가 조회와 무상관).
- 댓글·리포스트 거의 0 → 죽은 신호.

**스하리 (8건)** raw 조회/좋아요/댓글: `122/16/14 72/7/6 124/12/11 127/6/4 389/22/18 853/46/41 517/29/22 891/50/46`
- 조회·좋아요·댓글·리포스트 **일관되게 동반 상승 = 분리 가능한 진짜 신호.** 댓글 4~46 살아있음.

**계정별 표본**: 종류당 1~3개뿐 → **계정별 기준선 불가, 풀 전체(종류별) 기준 필수.**

**깨진 뇌피셜(폐기)**: ①계정별 p70 ②engagementScore(=좋아요/조회 rate)를 승자로 — rate는 **역방향**(5조회4좋아요=1.4 최고, 3024히트=0.03 바닥) ③쇼핑에 댓글·리포스트 가중.

## 3. 설계

### 3.1 유닛 구조
```
PostInsightSnapshot(24h·72h) → ① performance-scorer → { ② copy-learning, ③ propagation-planner }
```
각 유닛은 단일 책임 · 독립 테스트 가능.

### 3.2 ① performance-scorer (순수 함수)
입력: PUBLISHED 게시글의 최신 스냅샷(72h 우선, 없으면 24h).
- **쇼핑 점수 = 조회(views)** (리치 우선). 좋아요는 동점 처리.
  - winner = 조회 ≥ 쇼핑풀 중앙값 × 5 **그리고** 조회 ≥ 200(절대 바닥). 배수 규칙이라 스케일 무관.
  - loser = 조회 ≤ 풀 하위 30%.
- **스하리 점수 = 좋아요 + 댓글 + 리포스트** (합산 크기).
  - winner = 스하리풀 상위 30%(p70↑). loser = 하위 30%.
- 표본 부족(종류 풀 < 5)이면 전원 neutral(판정 보류).
- 출력: `{ postId, kind, score, rank: 'winner'|'neutral'|'loser', basis }`.

### 3.3 ② copy-learning
- **스하리: 즉시 가동.** winner 스하리 본문을 카피라이터 few-shot에 "우리 실제 성공작"으로 주입(트렌드 few-shot 위에 얹음) + winner에서 "왜 터졌나" 요인 1~2개 LLM 추출해 힌트로. loser 오프너는 회피 목록에 추가.
- **쇼핑: 보류.** winner 1개라 학습 신호 부족. winner 발생 시 표시만. 풀이 커지면(쇼핑 winner ≥ 3) 동일 방식 활성화.

### 3.4 ③ propagation-planner
- 트리거: 한 게시글이 **24h·72h 둘 다 winner**.
- 실행: 그 게시글의 상품/벤치마크 재사용, **계정별 카피 재생성**으로 타 적격 계정에 승인 카드 시차 생성.
- 제약 준수: 14일 동일상품 중복 금지 · 성별 라우팅 · 계정 1일 캡 · 동시발행 금지(시차). 자동 발행 아님(수동 승인).

### 3.5 콜드스타트 · 활성화
- 전 구간 풀 백분위 + 절대 바닥. 스하리 학습·확산 즉시 가능. 쇼핑은 아웃라이어만.
- 정적 프롬프트 유지 → 데이터 쌓이며 자동으로 학습 신호 강해짐.

## 4. 검증 (실 데이터 시뮬레이션 · 예측 금지)

performance-scorer를 실 25건에 돌려 다음을 **assert**:
- 쇼핑: 3024/81 = winner, 5~127 클러스터 = neutral, 최저 조회 = loser.
- 스하리: 853/891/517 상위 = winner, 72/127 하위 = neutral/loser.
- propagation-planner: 3024 winner에 대해 적격 계정(성별·14일중복 통과)만 카드 후보 생성, 이미 그 상품 쓴 계정은 제외.
- 시뮬레이션은 실제 DB 데이터로 · 카드 발송/발행 side-effect 없이 dry-run.

## 5. 남은 작업 · 데이터 이슈
- sookck 쇼핑 92h 스냅샷 1건 백필(성과 fetch 재시도).
- 쇼핑 학습은 표본 축적 대기(현재 winner 1).
- DAILY(일상) 파이프라인 미착수 → 스코어러는 kind 무관 설계하되 DAILY 규칙은 추후.

## 6. 단계 (phasing)
1. performance-scorer 구현 + 실데이터 시뮬레이션 (본 문서 §4).
2. copy-learning 스하리 가동 + A/B(피드백 on/off) 실측 비교.
3. propagation-planner (24h·72h winner → 시차 카드).
4. 쇼핑 학습 활성화(표본 임계 도달 시).
